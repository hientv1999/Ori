# Ori — Orion PC App

**Orion** is the PC companion app that pairs with Ori over BLE — **one codebase for both Windows and macOS**: Tauri v2 (Rust backend + OS webview — WebView2 on Windows, WKWebView on macOS), decided 2026-07-08, superseding an earlier WinUI 3 + SwiftUI split (see `memory.md`). Rust was chosen over a cross-platform framework like Flutter for native BLE access via `btleplug` (no plugin layer) and minimal background-service footprint. The UI (`PC_app/orion/src/`) is identical on both platforms; platform differences live inside the Rust backend (`PC_app/orion/src-tauri/`) behind `#[cfg(target_os = ...)]`, calling each OS's native APIs directly (WinRT Bluetooth/GSMTC/WASAPI on Windows, CoreBluetooth/MediaRemote/CoreAudio on macOS). Everything in this file is the shared feature/protocol spec the backend must satisfy — platform-specific API calls are called out per bullet as **Win:** / **mac (planned):**. Install URL shown during setup: `ori.app/orion`. App icon: the Ori wordmark.

A reference implementation of everything below (minus real calendar/Graph/OS integration) lives in `tools/mock_orion_ble.py` (BLE sync) and `tools/mock_orion_ota.py` (USB CDC firmware update) — when in doubt about exact wire behavior, those scripts are runnable proof of one valid implementation.

## Role

Orion is the authoritative data source for Ori. While running and synced, it pushes:

- Profile (name, job title, email, phone, photo)
- Today's meeting list
- Next Time Off entry (start, end, destination image)
- Current local time + timezone
- Microsoft Teams presence
- Shortcut icon assignments (Controls mode)
- Clock face preference (Digital/Analog)
- ANCS notification filter level

Orion also **reads** from Ori:
- **Firmware Revision String** characteristic (BLE SIG standard Device Information Service, `0x180A`/`0x2A26` — `ble-protocol.md` §3.1): a plain UTF-8 semver string, how Orion learns the running firmware version. Compared against the latest release at `ori.app` for the optional "Install update" prompt; re-read after a successful update to confirm. Version check rides BLE; the image transfer itself is USB CDC only (`ota.md`).
- **Device Settings** characteristic (char `000E`): read once on every (re)connect to recover `clock_face` and `ancs_filter` — the two NVS-persisted values whose ground truth lives on Ori. Orion uses these to populate its settings UI correctly without needing to cache what it last wrote across app restarts or BLE drops. See §6.4 in `ble-protocol.md`.

When Orion is not running, Ori falls back to cached data. See `connectivity.md` for the sync state model and `setup-flow.md` for the pairing flow.

## What the PC App Must Implement

- **BLE central role**: discover, pair (6-digit passkey confirmation UI), and maintain a bonded connection to Ori. Negotiate ATT MTU to 247 bytes on connect, falling back to 23 if refused. Persist bond records.
  - **First-pair handshake timing**: a valid `SyncControl{op:"BEGIN"}` sent within ~5 s of bonding is Ori's proof that the bonded peer is genuinely Orion (`ble-protocol.md` §6.1) — Ori commits the bond address on that BEGIN and drops any peer that bonds but never sends one in time. Orion must kick off the initial sync immediately after the passkey is confirmed, not lazily.
- **Initial + delta sync (hash-manifest)**: implement the unified sync flow in `ble-protocol.md` §6.1/§6.2 — on first pair, write everything inside one `SyncControl{BEGIN..END}` session; on every reconnect, write a `SyncManifest` of SHA-256 hashes per section (profile/photo/meetings/to), read back which sections Ori says it needs, and send only those (Time Sync and Device Settings — shortcuts + presence — ride along unconditionally on every (re)connect outside the BEGIN/END pipeline, like the mock's `run_sync()`). Stream Profile Photo / Meeting List / Time Off Entry / Media Album Art **Write-No-Response** with a Write-with-response checkpoint every ≤ 32 fragments (~7.6 KB window) — see `ble-protocol.md` §5.
- **Calendar data**: read today's meetings from the user's calendar and push to Ori. Cancelled meetings removed; past meetings drop off the device automatically. Hash-check against the manifest before resending (§6.3: on calendar event or every 15 min).
- **Time Off**: push the user's next Time Off entry with destination metadata and image. Resize the destination photo to **528×396**, JPEG, hard cap 512 KB (`ble-protocol.md` §10) before sending.
- **Time sync**: push current local time on every sync, and again every 10 min while connected (`ble-protocol.md` §6.3). The `tz` field is a **POSIX TZ string, not an IANA name** — Ori feeds it straight into `setenv("TZ", tz)`/`tzset()`, which silently falls back to UTC on an IANA string like `"America/Los_Angeles"`. Derive a fixed-offset POSIX string from the local UTC offset (e.g. `"PST8"`, `"LOC-2"`); see `_local_posix_tz()` in `tools/mock_orion_ble.py` for a reference implementation. No DST rule is required since Orion re-syncs periodically.
- **Microsoft Teams presence**: read the signed-in user's presence via Microsoft Graph (`GET /me/presence`) and push via the **Device Settings** characteristic (char `000E`, key `"p"`, `ble-protocol.md` §3/§6.4). Teams → Ori mapping:
  - `Available` → `0x00`
  - `Busy`, `DoNotDisturb`, `BusyIdle`, `InACall`, `InAMeeting`, `InAConferenceCall`, `Presenting`, `UrgentInterruptionsOnly` → `0x01`
  - `Away`, `BeRightBack`, `AwayIdle` → `0x02`
  - `Offline`, `PresenceUnknown`, `OffWork`, `OutOfOffice` → `0x03`
  - **Push a fresh value immediately on every (re)connect** — Ori does not return presence on Device Settings read (presence is ephemeral; Orion is the sole source of truth). On BLE drop, Ori immediately displays Offline regardless (`ble-protocol.md` §6.4).
  - Push cadence thereafter: subscribe to Graph change notifications (`/subscriptions` on `/communications/presences/{id}`); fall back to polling every ~60 s. Only write to BLE when the mapped byte actually changes.
  - OAuth: user signs into Microsoft account during setup and grants `Presence.Read`. Cache the refresh token in OS-native secure storage (**Win:** Windows Credential Locker; **mac, planned:** Keychain). On grant expiry/revocation: write `0x03 OFFLINE` to Ori, surface re-auth prompt in settings.
  - If Graph returns no presence data (non-corporate accounts, Teams not installed): write `0x03 OFFLINE` silently. The setup wizard makes the Teams-presence step skippable.
- **Profile management**: capture name, job title, email, phone, photo; push on initial pairing and on change. **Enforce input limits in the UI** — name ≤ 32 characters, job title ≤ 32 characters, email ≤ 32 characters, phone ≤ 16 characters (live counter; field blocks at limit — a frontend concern, e.g. `app.js`'s `cc()` counter/blocker; not a Rust backend check). The Rust backend intentionally does not re-validate these caps — it trusts its own frontend as the sole caller of `save_profile`/`ble_submit_passkey`, so this is not a gap to close on the backend side. Resize the profile photo to **228×228**, JPEG, hard cap 200 KB (`ble-protocol.md` §10) before sending. Wire-level byte caps are in `ble-protocol.md` §10.
- **Clock face preference**: settings subscreen (Digital / Analog). Selecting an option enables a **Save** button in the subscreen header; Back or Esc discards the pending selection. On Save, writes to Ori via **Device Settings** (char `000E`, key `"c"`, `ble-protocol.md` §3/§6.4) — only when the user changes it (Ori persists to NVS). **On every (re)connect, Orion reads Device Settings** to recover the current `clock_face` value so the subscreen reflects the device's actual setting without Orion having to cache what it last wrote.
- **ANCS notification filter**: settings subscreen (Disabled / Call Only / Important / All). Same Save/Discard header pattern as Clock Face. On Save, writes to Ori via **Device Settings** (char `000E`, key `"f"`, `ble-protocol.md` §3/§6.4) — only on change (NVS-persisted on Ori). Orion reads on (re)connect to recover the current `ancs_filter` value. Mapping: `0` = Disabled, `1` = Call Only (IncomingCall only), `2` = Important (IncomingCall or ANCS Important flag), `3` = All (default).
- **iPhone Info/Stats modal + ANCS drill-down**: tapping the header phone icon (bonded, connected or not) opens a snapshot mirroring Ori's own — name, connection dot, live signal bars, missed-calls/messages/notifications counts (from `PhoneBondStatus`, char `000F`), and Unpair. The counts Orion displays are already filtered through `ancs_filter` before Ori sends them (the same gate Ori applies to its own on-device tile counts — `connectivity.md`), and update immediately on a filter change (`ancs_client::set_filter()` → `push_phone_stats()`) — Orion just displays what it's given, no local filter logic. **Live while open** (2026-07-11): every `PhoneBondStatus` notify — including the ~5 s RSSI poll, not just count changes — re-renders an already-open modal in place (`setPhoneBondStatus()` re-invoking `openIphoneInfoModal()`, safe/idempotent while already shown), so the signal bars and connection dot never sit stale for as long as the modal stays open; previously only the header phone icon reacted to these notifies. Tapping a non-zero count opens a filtered list of the underlying notifications (chars 16–17, `ble-protocol.md` §13) — content and call state Ori already filtered through `ancs_filter` before sending, so Orion never needs its own copy of that filter logic, and the badge and the list it opens are always consistent with each other since both come from the same filter gate. **Resynced on every Orion (re)connect, not just a filter change** (`ancs_client::resync_orion_relay()` for char 16 / `resync_orion_call_state()` for char 17): chars 16/17 are notify-only with no read property and no replay of their own, unlike `PhoneBondStatus` — so without this, a notification (or an already-ringing/active call) present before Orion connected was counted in the aggregate but never actually reached Orion's local mirror, leaving a tile that showed a non-zero count with nothing behind it when tapped, or a call with no incoming/in-call view. **Fired from Ori's `onSubscribe()` GATT-server callback (char 16/17's own CCCD write completing), not the earlier `OrionConnected` event** — `OrionConnected` fires on encryption complete, before Orion's `run_sync` has even started; a resync notify sent that early is silently dropped (not subscribed yet) and never reaches Orion.

  **Reconnect resync race (found 2026-07, hardware log) and its two-part fix.** `onSubscribe` can fire from TWO different triggers, landing at very different times: (1) Orion's own explicit CCCD write, or (2) on a **bonded reconnect**, NimBLE's host stack itself — `ble_gatts_bonding_restored()` (`nimble/host/src/ble_gatts.c`) — restoring every persisted CCCD for the peer and re-firing the subscribe event the instant the encrypted link comes back up, **entirely server-side, with no new write from Orion required at all**. Trigger (2) doesn't exist on a first pairing (nothing persisted yet to auto-restore), only on reconnect — which is exactly the symptom that gave this away: `PhoneBondStatus`'s aggregate count (char 000F, read fresh on every connect) was always correct, but the drill-down list for every bucket came back completely empty, reproducible only on reconnect, never on first pair.

  Orion-side reordering alone **cannot** close this: trigger (2) is essentially instantaneous (fires as part of NimBLE's bonding-restore sequence, before Ori's firmware has even reached its own connection/service-ready state), while Orion's soonest possible subscribe still has to wait through `connect` → GATT service discovery → an encrypted read (the encryption probe) — unavoidably slower, no matter how early in its own code Orion calls `subscribe()`. Confirmed on hardware: even with `subscribe_ancs_relay_early()` (below) creating Orion's receiver as early as its code allows, Ori's log showed the resync firing and sending "clear" + every queued notification correctly, while Orion's receiver still wasn't alive yet — the burst was lost for the rest of that connection.

  **The real fix is on the firmware side**, in `state_machine::on_reconnect_end()` (`state_machine.cpp`) — fired only on a genuine reconnect's `SyncEnd`, never on first pairing, and causally guaranteed to happen *after* Orion has subscribed: Orion sends `SyncControl{END}` (what triggers this) only as the last step of `run_sync()`, which its Rust code always runs strictly after subscribing to chars 0010/0011. It calls `ancs_client::resync_orion_relay()`/`resync_orion_call_state()` a second time, unconditionally. Both are idempotent (a full clear + re-add of whatever's currently queued/live, identical to an ordinary filter-change resync), so firing them again on top of a first resync that DID land is a harmless refresh, not a correctness risk — and on the (now-more-common) case where trigger (1)'s early resync missed its window, this second one is guaranteed to land.

  Orion's own `subscribe_ancs_relay_early()` (`central.rs`) — creating both receivers and subscribing to both characteristics as early as the link is proven-encrypted, *before* `run_sync` starts, in both `reconnect()` and the first-pairing path `submit_passkey` — is kept as a genuine (if insufficient alone) improvement: it removes all the OTHER latency Orion's own code used to add (previously not subscribing until `start_post_sync_tasks`, spawned *after* the whole sync completed), and is what guarantees the receiver is already alive and ready in time for the firmware-side fix's guaranteed-late resync above. `start_post_sync_tasks` takes the pre-made streams and hands them to the watcher tasks instead of letting those tasks create their own this late. Tapping a row opens a detail view (silent badge top-left, close always top-right, dynamic Answer/Decline/Dismiss/Read-all buttons built from the notification's own `pos_label`/`neg_label`/`has_neg_action` — **never hardcoded**) or, for a still-ringing/active call, the call view instead. **If Ori reports the open detail's notification removed (`AncsNotification{op:"remove"}`) while it's on screen, Orion closes it and returns to the list** — never leaves a detail open for content that no longer exists on the phone. Notifications sharing the same app + title collapse into one row/detail with a stacked-count badge and a single "Read all" (mirrors `modal_ancs_notification.cpp`'s own stacking). Writes `AncsNotificationAction` (char `0012`) on every action tap; never updates its own UI optimistically — waits for the resulting `"remove"`/`AncsCallState` notify, same as every other state change in this protocol.
- **Incoming call takeover**: `AncsCallState{st:1}` (char `0011`) brings the Orion window to the foreground (show + focus + un-minimize) exactly as clicking its taskbar entry would, then shows the ringing view — the whole point is the user notices even if Orion was backgrounded. Never fires when `ancs_filter` is Disabled; Ori simply never sends the notify in that case, so Orion needs no filter check of its own here. `st:2` (active) resumes the in-call view with its duration timer seeded from the relayed elapsed seconds, not restarted at zero. `st:0` closes whatever call view is open. The ringing/in-call view and the header call chip (below) both render the **calling app's real icon** from `AncsCallState`'s `"k"` icon token (`ble-protocol.md` §13) — the same brand-asset map as ANCS notifications, falling back to a generic call glyph — never the generic glyph when a recognised token is present. An already-ringing or already-active call present **before Orion connects** shows immediately on connect via Ori's call-state resync (`resync_orion_call_state`, `ble-protocol.md` §13), same path as the notification-mirror resync.
- **Header call chip**: while a call is ringing/active, a quick-access chip showing the calling app's icon appears in the header **to the left of the phone icon**; clicking it reopens the ringing/in-call view (so the user can re-check caller identity and running call time after dismissing the full modal with its close button). Hidden whenever there's no live call. The in-call duration timer runs independently of whether the modal is open, so reopening shows the live elapsed time, never a reset one. **Ring color mirrors Ori's own status-bar call tile exactly**: a solid (non-animated) yellow ring (`st:1`, `.ringing`) while the call is still ringing/unanswered, switching to solid red (`st:2`, `.on-call`) the instant it's answered/active — `styles.css`'s `--call-ring-ringing`/`--call-ring-active` are pixel-matched to firmware `theme.h`'s `COLOR_CALL_RINGING`/`COLOR_DANGER` so the same call reads identically on both screens.
- **Close ANCS/call surfaces on link loss**: when the Ori link drops (`conn-state: "off"`), Orion force-closes every ANCS-derived surface — the drill-down list, its detail overlay, the ringing/in-call view (stopping the duration timer), and the iPhone Info hub — since their content is relayed from Ori and can no longer be verified or acted on (an `AncsNotificationAction` write would just fail). This is done **only** on a sustained disconnect, not on the transient Connecting/Syncing reconnect phases: those are reconciled by Ori's own resync (clear + re-add for notifications, a fresh `AncsCallState` for calls), so a still-live call/notification reappears automatically on reconnect rather than being closed-then-reopened as a flicker.
- **Background operation**: Orion has **no main window** — its only UI surface is a compact, movable, frameless panel (`memory.md`'s "Orion UI model", revised 2026-07-08). It auto-opens on launch, stays visible until the user explicitly minimizes it (in-app minimize button or tray icon), and shows a normal taskbar entry while open — it does NOT auto-dismiss on click-away. No native title bar or resize; the custom titlebar doubles as the drag handle. Implemented via Tauri's `tray-icon` feature on both platforms (`src-tauri/src/lib.rs`). The app stays running and synced whether or not the panel is open. Option to start at user login (`tauri-plugin-autostart`).
- **Passkey entry UI (Windows)**: custom in-app modal — six single-digit boxes with auto-advance focus and paste support (`setup-flow.md`). Ori displays the 6-digit passkey on its own screen; the user types it into this modal, which drives WinRT's `DeviceInformationCustomPairing` (`PairingRequested` → `ProvidePin`) so the OS bonds against the typed code — Orion is the entry side, Ori is the display side (LE Secure Connections Passkey Entry, not a mutual-display confirm). Revised 2026-07-08 (`memory.md`) — an earlier pass wrongly generalized macOS's constraint to Windows and used the OS's own pairing prompt on both platforms; Windows doesn't need that fallback. **macOS has no equivalent** — CoreBluetooth exposes no app-level pairing UI hook — and is deferred, not designed, until that build (M6b) starts.
- **Reset**: single settings button, gated by one confirm dialog offering two destructive actions:
  - **Factory Reset** — writes the Factory Reset Command over the bonded link; Ori wipes its own NVS + bonds and reboots into setup, and Orion drops its local bond record (`ble-protocol.md` §7.2). Orion's local profile cache is untouched.
  - **Clear All** — does the above, and additionally clears Orion's local cache (profile, calendar sign-in, shortcut config), then walks the user back through first-run setup.
- **Firmware update (optional, user-initiated)**: polls `ori.app` for the latest version, compares to `fw_version` read from the standard Firmware Revision String characteristic (`ble-protocol.md` §3.1), shows "Install update" when newer exists. Full sender algorithm (`OriFwVer=` marker extraction, VID `0x303A` port discovery, DTR assertion, windowed flow control, reject/fail table) is in `ota.md`; `tools/mock_orion_ota.py` covers all 9 failure scenarios. If no serial port: prompt "Plug Ori into this PC, then try again."
- **Controls-mode OS bridge + state push**: implement per `ble-protocol.md` §12 (canonical API table, swipe race conditions, reconnect semantics). Key requirements: subscribe to `Keyboard Command` notifies; translate each op to the appropriate OS API; after `vol_set` always write `HostVolumeState{level:N}` back to Ori. Shortcut actions (exactly 14): `vol-mute` (mute audio), `mic-mute` (mute mic), `screenshot` (display label "Snip Tools" in Orion's UI — wire token unchanged), `lock-screen`, `favorite-1`/`favorite-2`/`favorite-3` (three independently user-configured actions, each with its own combo), `calculator` (launch the OS calculator app), `copy`/`cut`/`paste`/`undo`/`redo`/`save` (fixed standard edit shortcuts — Ctrl+C/X/V/Z/Y/S). **mac (planned):** `play_pause`/`prev`/`next` require Accessibility permission on first launch; `seek` and track-change use private `MediaRemote` — distribution-safe but re-verify per OS version. State push: on (re)connect push current `HostVolumeState` + current track (`MediaMetadata`, or empty if nothing playing); on change push via OS callbacks (volume debounce ~100 ms; track change writes `MediaMetadata` + art resized 484×216 JPEG chunked to `MediaAlbumArt`). Push `playing` on every track change AND every play/pause toggle. PC-side seek: if position deviates > ~5 s from dead-reckoned while playing, push corrected `MediaMetadata` with `position_s`/`duration_s`.
- **Media-mode shortcut configuration UI**: settings subscreen with three slot rows, each with a dropdown (Volume Mute / Mic Mute / Snip Tools / Lock Screen / Calculator / Copy / Cut / Paste / Undo / Redo / Save / Favorite 1 / Favorite 2 / Favorite 3) and an icon preview. The host-side action mapping is local to Orion. Selecting any **Favorite N** reveals that slot's own keyboard combo recorder — combos are per-slot, not per-token, so e.g. Favorite 1 in Slot 2 and Favorite 1 in Slot 3 (an unusual but permitted choice) would independently record their own combos: click to arm, press the desired key combination (modifier+key), Esc to cancel without changing. The subscreen uses the same Save/Discard header pattern as Clock Face and Notification Filter — Save is enabled when any slot or combo has changed; Back/Esc discards all pending changes. **Favorite-empty guard:** Save stays disabled the whole time any slot is set to a Favorite with no combo recorded yet — there is no revert-on-save path, since Save can never be clicked while that condition holds. The chosen icon token for each slot is written to Ori via **Device Settings** (char `000E`, keys `"1"`/`"2"`/`"3"`, `ble-protocol.md` §3/§12) — outside the BEGIN/END staging pipeline, **persisted to NVS on Ori**. Orion reads Device Settings on every (re)connect to recover the current slot tokens and only writes when the user changes a slot — see `ble-protocol.md` §6.4.
## Panel layout

Orion's only UI surface is a 348 px wide tray-anchored flyout panel. The body is split into two visibility zones:

### Always visible (connected and disconnected)
- **Profile card** — circular presence-bordered photo (228×228 px), name, presence badge. Tapping opens the profile editor subscreen (Save/Back; live character counters at the Orion-enforced input caps).
- **Time Off** — separated from the profile card by a divider; toggle + collapsible destination card (image, destination, date range). Tapping opens the Time Off editor subscreen (Save/Back).
- **Firmware update indicator** — shown in the header as an icon only when a newer version is available; tapping opens the firmware update flow (Orion fetches `.bin` from `ori.app`, sends via USB CDC).

### Visible when Connected or Disconnected — hidden only during Connecting/Syncing (`connRequiredSections`)
These four rows and their subscreens (2026-07-11: revised from "connected and synced only" — see below) are hidden **only** during **Connecting** and **Syncing** — the two states between "Ori was just found" and "the sync that would make its values trustworthy has actually finished." A gated subscreen left open when either of those states starts is force-closed (`dismissTransientScreen()`) since its entry row just vanished out from under it.
- **Notification Filter** — single-select subscreen with Save/Discard pattern.
- **Clock Face** — single-select subscreen with Save/Discard pattern.
- **Time Format** — single-select subscreen (24-hour / 12-hour) with Save/Discard pattern.
- **Quick Actions** — three-slot subscreen with Save/Discard pattern and a per-slot keyboard combo recorder for whichever slots are set to Favorite 1/2/3.

**Disconnected is different from Connecting/Syncing: the rows stay visible and editable.** The user can open any of the four subscreens and hit Save with no live link at all — Orion just can't confirm the value against Ori in that moment. Rather than block editing until the next connection, `save_device_settings` (`commands.rs`) persists the pending value into Orion's own local store first (`store::SavedState::pending_clock_face`/`pending_time_format`/`pending_ancs_filter` — survives an app restart, not just the current session) and then best-effort attempts the live BLE write; a failure there (expected while disconnected) is swallowed rather than surfaced as an error, since offline editing is the intended path, not a failure case. `run_sync` (`central.rs`) flushes any pending value to Ori as part of the very next successful reconnect/sync, right alongside the (pre-existing) unconditional shortcuts push, and clears the pending flag once delivered. Quick Actions needs none of this machinery: its icon-slot tokens were already pushed unconditionally on every reconnect regardless of local dirty-state (ble-protocol.md §6.3 "Shortcuts — always"), so an offline edit there already had a guaranteed delivery path.

On transition into Connected (including after a Syncing period), Orion re-reads Device Settings from Ori (§6.4) to repopulate the rows — by that point any pending edit has already been flushed by `run_sync` above, so this read reflects the just-delivered value, never a stale pre-edit one.

### Settings subscreen UX convention (Save/Discard)
All three settings subscreens share this header + interaction pattern:
- Header: **Back** (left) · title (centre) · **Save** (right, disabled until a change is made).
- Selecting an option or recording a combo does **not** apply immediately — it only arms the Save button.
- **Back / Esc with no pending change**: returns immediately, no prompt.
- **Back / Esc with a pending, unsaved change**: shows a "Discard changes?" confirmation modal — **Keep editing** returns to the subscreen with the pending change intact; **Discard** reverts to the last-committed value and returns to the panel without writing to Ori.
- **Save**: commits the pending state, writes to Ori via Device Settings, returns to the panel.

Profile and Time Off subscreens use the same Save/Discard-with-confirmation convention but are accessible regardless of connection state.

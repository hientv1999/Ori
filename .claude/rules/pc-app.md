# Ori — Orion PC App

**Orion** is the PC companion app that pairs with Ori over BLE — **one codebase for both Windows and macOS**: Tauri v2 (Rust backend + OS webview — WebView2 on Windows, WKWebView on macOS), decided 2026-07-08, superseding an earlier WinUI 3 + SwiftUI split (see `memory.md`). Rust was chosen over a cross-platform framework like Flutter for native BLE access via `btleplug` (no plugin layer) and minimal background-service footprint. The UI (`PC_app/orion/src/`) is identical on both platforms; platform differences live inside the Rust backend (`PC_app/orion/src-tauri/`) behind `#[cfg(target_os = ...)]`, calling each OS's native APIs directly (WinRT Bluetooth/GSMTC/WASAPI on Windows, CoreBluetooth/MediaRemote/CoreAudio on macOS). Platform-specific calls below are marked **Win:** / **mac (planned):**. Install URL shown during setup: `orinari.net/orion`. App icon: the Ori wordmark.

A reference implementation of everything below (minus real calendar/OS integration) lives in `tools/mock_orion_ble.py` (BLE sync) and `tools/mock_orion_ota.py` (USB CDC firmware update) — runnable proof of one valid implementation when in doubt about wire behavior. `tools/parse_sharing_metadata.py` and `tools/test_ics_calendar.py` are reference implementations of the two halves of the calendar source specifically (see below): reading the fields out of an Outlook sharing-invitation XML, and fetching + parsing the resulting ICS feed (including recurrence expansion).

## Role

Orion is the authoritative data source for Ori. While running and synced, it pushes:

- Profile (name, job title, email, phone, photo)
- Today's meeting list
- Next Time Off entry (start, end, destination image)
- Current local time + timezone
- Shortcut icon assignments (Controls mode)
- Clock face preference (Digital/Analog)
- ANCS notification filter level
- Weather condition + temperature + day/night + precipitation intensity (`weather.rs`, below)

Orion also **reads** from Ori:
- **Firmware Revision String** characteristic (BLE SIG standard Device Information Service, `0x180A`/`0x2A26` — `ble-protocol.md` §3.1): plain UTF-8 semver, how Orion learns the running firmware version. Compared against the latest `orinari.net` release for the optional "Install update" prompt; re-read after a successful update. Version check rides BLE; the image transfer is USB CDC only (`ota.md`).
- **Device Settings** characteristic (char `000E`): read once on every (re)connect to recover `clock_face` and `ancs_filter` — the two NVS-persisted values whose ground truth lives on Ori — so Orion's settings UI is correct without caching what it last wrote. Also subscribed: Ori notifies this same characteristic whenever its own live `signal_bars` bucket changes, which the Ori Info modal uses in place of a poll. See §6.4 in `ble-protocol.md`.

When Orion is not running, Ori falls back to cached data. See `connectivity.md` for the sync state model and `setup-flow.md` for pairing.

## What the PC App Must Implement

- **BLE central role**: discover, pair (6-digit passkey confirmation UI), maintain a bonded connection. Negotiate ATT MTU to 247 bytes, falling back to 23 if refused. Persist bond records.
  - **First-pair handshake timing**: a valid `SyncControl{op:"BEGIN"}` within ~5 s of bonding is Ori's proof the bonded peer is genuinely Orion (`ble-protocol.md` §6.1) — Ori commits the bond address on that BEGIN and drops any peer that never sends one in time. Orion must kick off the initial sync immediately after the passkey is confirmed, not lazily.
- **Initial + delta sync (hash-manifest)**: implement `ble-protocol.md` §6.1/§6.2 — first pair writes everything inside one `SyncControl{BEGIN..END}` session; every reconnect writes a `SyncManifest` of SHA-256 hashes per section, reads back which sections Ori needs, sends only those (Time Sync and Device Settings ride along unconditionally outside BEGIN/END, like the mock's `run_sync()`). Stream Profile Photo / Meeting List / Time Off Entry / Media Album Art **Write-No-Response** with a Write-with-response checkpoint every ≤ 32 fragments (~7.6 KB window) — `ble-protocol.md` §5.
- **Calendar data — Outlook sharing-XML + ICS feed, deliberately NOT Microsoft Graph/OAuth**: Ori's calendar source does not use Microsoft Graph, Azure AD app registration, or OAuth of any kind — decided 2026-07-16 after the Graph path was fully built and verified working (`tools/mock_orion_teams`) but ruled out for this product regardless. The replacement:
  1. **User obtains a sharing invitation.** Concrete path Orion's own UI walks the user through (the setup wizard's calendar step and Settings → Calendar Source both link to this via a "How do I get this file?" help modal): in Microsoft Teams, open the **Calendar** tab → **•••** (more options) → **Share** → enter a personal or external email address. Teams' Share action runs through Outlook/Exchange's own **publish** mechanism under the hood (`Provider Type="ms-exchange-publish"`) — the same thing doing this from Outlook desktop/web directly would produce — and attaches a `sharing_metadata.xml` file to the invitation email, a standard Exchange feature (schema `http://schemas.microsoft.com/sharing/2008`), not anything Orion generates or controls.
  2. **Orion imports that XML file** — Settings → Calendar Source → Microsoft → "Import Outlook calendar sharing file" (a full-width `.btn-block` button, not the narrow `.btn-full` pill every Cancel/Save pair elsewhere uses — this is the row's one and only action) opens a native file picker for the `.xml` attachment saved from step 1. Parsing is plain XML, no auth, no network call. Exact fields read (reference implementation: `tools/parse_sharing_metadata.py`):
     - `Initiator/Name` + `Initiator/SmtpAddress` → pushed as Profile Info `name`/`email` (same BLE path as manual entry, `ble-protocol.md` §4) — this is what replaces manually typing name/email during setup. Job title and phone aren't in the XML and still need manual entry.
     - `Invitation/Providers/Provider/ICalUrl` → the calendar feed URL, persisted locally (`store.rs`) as the calendar source. Everything else in the file (`EntryId`, `BrowseUrl`, `TargetRecipients`) is parsed for context only, never stored or acted on.
  3. **Orion polls the ICS feed directly** — plain HTTPS GET, no authentication at all; the URL itself is the access control (anyone holding it can fetch the feed, so treat it with the same care as a password once imported). Reference implementation: `tools/test_ics_calendar.py`. Poll cadence: same ~15 min as the calendar-refresh cadence already used elsewhere (§6.3) — polling faster doesn't buy more freshness, see the staleness caveat below. This poll runs continuously for the app's whole lifetime (`calendar_import::spawn_poll_task`, spawned once at startup), **independent of and concurrent with** the BLE reconnect attempt — whichever finishes first doesn't wait for the other:
     - **Calendar data ready before Ori reconnects:** no special handling needed — `run_sync` (§6.1/§6.2) always reads whatever's currently cached at the moment it actually runs, so the freshly-polled meetings just ride along in that same sync.
     - **Calendar data changes while Ori is already connected** (a later poll tick, or the user re-importing/disconnecting in Settings): a full reconnect might not happen again for a long time, so waiting for one would leave Ori showing stale meetings indefinitely. Instead, Orion diffs the newly-fetched list against what's cached (`BleState::replace_cached_meetings`) and, only on an actual change, pushes a live update immediately via its own BEGIN/END session scoped to just Meeting List (`ble::central::push_meetings` — same "already know it's needed, no manifest round-trip" reasoning as the Profile/Time Off live-push functions below it). This is the concrete implementation of §6.3's "Meeting List | Calendar event or every 15 min | push if needed" row. If Ori isn't reachable at that exact moment, the push is a no-op — the cache is already updated regardless, so the next reconnect's `run_sync` sends it instead.
  4. **Recurring events must be expanded, not read as raw VEVENT blocks** — a single VEVENT carrying an RRULE represents a whole series (e.g. "every Monday"), not one meeting. Naively taking the first N VEVENT blocks in file order conflates series with occurrences. Rust: the `icalendar` crate for parsing + the `rrule` crate for recurrence expansion (mirrors `test_ics_calendar.py`'s use of `recurring_ical_events` in Python).
  5. **Filter to today's local date, map to `Meeting`** (`ble-protocol.md` §4): `i`=UID, `s`/`e`=start/end epoch, `t`=SUMMARY (truncated to the wire cap), `l`=LOCATION (truncated). **`o` (organizer) is always sent as `""`** — published/shared Exchange ICS feeds strip organizer and attendee data entirely; there is no source for this field on this calendar path, and this is not a bug to fix. Push via the existing Meeting List characteristic exactly as before — no BLE protocol change from the originally-planned Graph-based design, only the data source changed.
  6. **Known, accepted limitation: staleness.** Published Exchange calendar feeds carry no refresh SLA from Microsoft — real-world lag is commonly hours, occasionally a full day, not minutes. This is a deliberate tradeoff (it entirely avoids Azure AD app registration and OAuth) and the Calendar Source settings screen should say so plainly — e.g. "Calendar updates may take a few hours to appear" — so a same-day meeting not showing up promptly reads as expected behavior, not a bug.
  7. **Re-importing** a fresh XML (e.g. after re-sharing, or the link was rotated) simply overwrites the stored `ICalUrl` — no special-case handling needed. **There is deliberately no separate Disconnect action** on the Settings → Calendar Source screen (removed 2026-07-16) — re-importing is the only way to change a connected source; a full Settings → Reset → Clear All is the only way to wipe it back to disconnected. The Google Calendar row on this same screen is a permanently disabled `.cal-opt`-adjacent placeholder — a full-width `.btn-block` **Coming soon** button, `calInfo.gg.ok` always `false` — identical treatment to the setup wizard's own Google Calendar row (below); no real integration exists yet for either.

  **Weather data — keyless, fully automatic, no Settings UI** (`weather.rs`): the same "no signup, no API key, no OAuth" reasoning as the calendar path above applies here too.
  1. **Location, resolved once per app launch** (a desk-based PC doesn't move mid-session, `product-intent.md`): the frontend's `requestWeatherLocation()` (`app.js`) calls the browser's own `navigator.geolocation.getCurrentPosition()` (backed by Windows Location Services / macOS CoreLocation through WebView2/WKWebView — no Tauri plugin needed) and reports the result via `set_weather_location` (`commands.rs`). On denial, timeout, or if geolocation isn't available at all, it reports `null`/`null` instead, and `weather.rs` falls back to IP-based geolocation (`ipapi.co` — keyless, returns lat/lon and country in one call). Called from two places: the setup wizard's own location-permission step (step 3 below) on a first-run pair, and unconditionally right after `get_initial_state()` resolves on every later, already-paired launch.
  2. **Temperature unit is inferred from country, not user-configurable** — a precise `navigator.geolocation` result is reverse-geocoded via `api.bigdatacloud.net` (keyless, built specifically for this "browser geolocation → country" pairing) to learn the country for this heuristic, since GPS coordinates alone don't carry one; the IP-fallback path already gets country for free from `ipapi.co`. Fahrenheit for the standard short list of countries that default to it (US, Bahamas, Belize, Cayman Islands, Liberia, Palau, Micronesia, Marshall Islands); Celsius everywhere else. Wrong for someone (e.g. an expat, or over a VPN), the fix is a real Settings toggle later — not attempted here, since weather has no Settings surface at all today.
  3. **Weather itself comes from Open-Meteo** (`open-meteo.com` — free, keyless): current temperature (requested pre-converted to the unit from point 2, no manual math) + a WMO weather-interpretation code, mapped down to Ori's 7-value `weather_condition` enum (`weather.rs`'s `map_wmo_code` — several WMO codes collapse onto the same Ori bucket, e.g. every drizzle/rain-shower variant → `Rain`).
  4. **`is_night` and `intensity` are derived from the same Open-Meteo call, no new request.** `is_night` is Open-Meteo's own `is_day` field, inverted (`weather.rs`) — already returned alongside the WMO code, so it costs nothing extra. `intensity` is a finer bucketing of the SAME WMO code `map_wmo_code()` already maps to `weather_condition` — the WMO table already distinguishes qualifiers like drizzle vs. rain vs. heavy rain, or slight vs. moderate vs. heavy snowfall, which `map_wmo_code()` collapses onto Light/Moderate/Heavy for Rain/Thunderstorm/Snow; Fog only ever resolves to Light/Heavy since there are just two real fog WMO codes to draw from (no Moderate). Every other condition (Clear/PartlyCloudy/Cloudy) has no intensity axis and always sends `0`/None.
  5. **Polled every ~15 min**, same cadence as calendar (§6.3) — re-fetches weather for whatever location was resolved in point 1, and only writes through to Ori (`ble::set_device_settings`, char `000E`, keys `"w"`/`"n"`/`"i"`/`"d"`/`"u"`) when the reading actually differs from what was last successfully pushed. Also re-sent as-is (no fresh fetch) on every (re)connect via `weather::push_last_known` (`start_post_sync_tasks`, `central.rs`) — weather rides outside the BEGIN/END pipeline entirely (§6.4) so `run_sync` never touches it, meaning every (re)connect needs its own explicit push, same reasoning as the calendar's live-resync-on-change design just above. Either push is best-effort: not connected right now just means the next (re)connect's `push_last_known` sends it instead, since the cache is already updated regardless of whether the live push landed.

  **Local holiday support — computed, not fetched, no Settings UI** (`holiday.rs`): Ori's calendar icon (no-meetings screen) and month view highlight local holidays in `--danger` red (`screen-layout.md`/`state-machine.md`). Firmware does almost all of this itself, with zero BLE dependency: `holiday_data.cpp` carries compiled-in rule tables (Fixed-date, Nth-weekday-of-month, Last-weekday-of-month, Weekday-immediately-before-a-date, Weekday-on-or-after-a-date, Easter-offset — the same Anonymous Gregorian/Computus algorithm used to compute Easter Sunday) for 8 countries — **US, Vietnam, Canada, UK, Australia, Spain, Mexico, France** — covering the primary country for each of Orion's 4 supported UI languages (English/Vietnamese/Spanish/French), selected by `holiday_country` (Device Settings `"g"`), **plus a regional layer** (`holiday_region`, Device Settings `"j"`) for well-documented subdivisions that genuinely differ from their national baseline — e.g. every Canadian province/territory's own Family Day variant, Quebec's National Patriots' Day (replacing Victoria Day) and Saint-Jean-Baptiste Day, the UK's Scotland/Northern Ireland-only bank holidays, every Australian state's own Labour Day date (there is no single national one), and each of Spain's 17 comunidades' own regional day. A region with no well-documented official difference (most US states, all of Mexico) is simply never populated — `holiday_region` resolves to 0/None there, same "don't guess" reasoning as an unsupported country. The one holiday no closed-form rule can express is Vietnamese Tet (lunar New Year) — unlike Easter's ecclesiastical approximation, a real lunisolar calendar needs actual astronomical lunar/solar-position data, not something to hand-roll and self-verify. Orion supplies this one piece:
  1. **Computed once per app session**, not fetched from any API — `holiday.rs` uses the `chinese-lunisolar-calendar` crate (MIT-licensed, range 1901–2101) to resolve every Lunar New Year date from 1970 through 2100 into a flat table of epoch-days (days since 1970-01-01, same convention `MeetingList.d` already uses). Verified against known reference dates (2024-02-10, 2025-01-29, 2026-02-17) in `holiday.rs`'s own unit tests rather than trusted blindly. Memoized in a `OnceLock` — the table never changes at runtime, so it's computed exactly once and reused for the rest of the session, then discarded on quit (Ori's own NVS cache is what makes it durable across restarts, not Orion's).
  2. **`holiday_country` and `holiday_region` are both derived from the SAME location `weather.rs`'s lookup already resolved** (`weather::country_code()`/`weather::region_code()`) — no second geolocation call for features that all just need "where is this PC." Triggered from the tail of `weather::set_location()` itself (`holiday::resolve_and_push`), the instant that resolution completes. `country_to_device_value()` maps the raw ISO 3166-1 alpha-2 code to `holiday_data::Country`: 0=None 1=US 2=VN 3=CA 4=GB 5=AU 6=ES 7=MX 8=FR (the UK's ISO code is `"GB"`, not `"UK"`); any other/unresolved country sends 0 — firmware has no rule table for it, so no highlighting is correct, not a placeholder guess. `region_to_device_value()` then maps the raw, country-prefix-stripped ISO 3166-2 subdivision code (`weather.rs`'s `strip_country_prefix()` — BigDataCloud's reverse-geocode returns it prefixed, e.g. `"CA-BC"`; ipapi.co's IP-fallback returns it bare, e.g. `"BC"`) to the per-country region code documented in `holiday_data.h`, dispatching on the already-resolved country value since a bare code like `"BC"` or `"AB"` only means something once the country is known. France is a deliberate gap: the Alsace-Moselle carve-out (`ble-protocol.md`'s `"j"` doc) is a *département*-level distinction (Bas-Rhin/Haut-Rhin/Moselle), finer than the *region*-level code these providers resolve (post-2016 merger, those départements now sit inside the broader "Grand Est" region alongside Champagne-Ardenne and Lorraine) — auto-detection would require department-level geocoding this app doesn't have, so `region_to_device_value()` always sends 0 for France; the firmware rule table exists regardless, for if the region is ever known some other way.
  3. **Pushed on every (re)connect**, the lunar table (Lunar Holiday List, char `0013`), `holiday_country` (Device Settings `"g"`), and `holiday_region` (`"j"`) together — `holiday::push_last_known`, called from `start_post_sync_tasks` alongside `weather::push_last_known`. No BEGIN/END staging for the lunar table (same simple treatment as Media Album Art, `ble-protocol.md` §5) — Ori commits it straight to NVS on chunk reassembly. All three pushes are best-effort and idempotent: since the table is session-cached and country/region rarely change, resending identical bytes costs nothing, so there's no "did this change" tracking the way Shortcuts/Clock Face do.
  4. **Fully offline after one successful sync.** Ori's NVS cache (`holiday_data::set_lunar_days()`/`set_country()`/`set_region()`) is what makes holidays render without Orion connected at all — Orion's own session-cached values are just the source for that one-time (per reboot-cycle) push, not something Ori depends on being live.
  5. **Known, accepted limitation: timezone-boundary divergence.** `chinese-lunisolar-calendar` computes the Chinese lunisolar calendar, referenced to the UTC+8 meridian; Vietnamese Tet is defined against UTC+7 and can, in rare years, fall a day earlier than Chinese New Year would. Not corrected — no per-year override table exists to special-case it, same spirit as the calendar path's accepted staleness tradeoff above.
  6. **No Settings UI, no user override** — matches weather's "fully automatic" precedent above. If a country/region guess is ever wrong for someone (e.g. an expat, VPN), the fix is a real Settings toggle later, not attempted here.

  **First-run setup wizard is four steps, calendar first:** Welcome → **1. Connect Calendar** → **2. Profile** → **3. Location Permission** → **4. Pair with Ori** (`su-step-calendar`/`su-step-profile`/`su-step-location`/`su-step-discover`, `PC_app/orion/src/index.html`+`app.js`). Step 1 is just the import card above (`.cal-import-card`) plus the "How do I get this file?" help modal (`m-cal-help`) walking through the Teams steps in point 1; **Next stays disabled until the import succeeds** — same "gate progress on completion" convention every other setup step already uses. Step 2 is the ordinary manual profile form (photo/name/job title/email/phone), with name/email pre-filled from step 1's result but still user-editable; job title, phone, and photo have no calendar source and are always manual. A **Google Calendar placeholder** (disabled `.cal-opt` row, "Coming soon") sits below the Outlook card on step 1 — reserved for a future real integration, not yet implemented.

  **Step 3 is a custom pre-permission explainer for weather.rs's location resolution** (`.loc-permit-ico`/`.loc-permit-title`/`.loc-permit-desc`) — a plain centered "Show local weather on Ori" screen with a **Not now** / **Allow** button pair (`.btn-row`, same left-secondary/right-primary convention as every Cancel/Save pair elsewhere in this app), both of which advance unconditionally (nothing here is worth gating Next on; weather is best-effort everywhere else in this app too). Exists because the REAL OS location-consent prompt (WebView2/WKWebView, backed by Windows Location Services/CoreLocation) can't be restyled — it's rendered natively, outside any web content, the same security boundary every browser's own permission prompts have — so this step's only job is to give the user context *before* that native prompt fires, not to replace it. "Allow" calls `requestWeatherLocation()` (app.js), the same function a returning (already-paired) launch calls unconditionally right after `get_initial_state()` resolves; "Skip" deliberately does NOT call it — the user just said no, so this session doesn't ask again, though a later restart (once paired) tries automatically regardless of what was chosen here.

  **What this deliberately does not do, and why:** Teams presence (Available/Busy/Away/Offline) has been removed from both Ori and Orion entirely as a consequence of this decision — the XML/ICS path has no live-presence data source, and Graph (the only thing that could have supplied one) is explicitly out of scope for this product. See `screen-layout.md`'s connection-status border for what replaced the old presence-coloured profile border.
- **Time Off**: push the next Time Off entry with destination metadata and image, resized to **528×396** JPEG, hard cap 512 KB (`ble-protocol.md` §10).
- **Time sync**: push current local time on every sync, and again every 10 min while connected (§6.3). The `tz` field is a **POSIX TZ string, not an IANA name** — Ori feeds it straight into `setenv("TZ", tz)`/`tzset()`, which silently falls back to UTC on `"America/Los_Angeles"`-style strings. Derive a fixed-offset POSIX string from the local UTC offset (e.g. `"PST8"`, `"LOC-2"`) — see `_local_posix_tz()` in `tools/mock_orion_ble.py`. No DST rule needed since Orion re-syncs periodically.
- **Profile management**: capture name, job title, email, phone, photo; push on pairing and on change. Name and email may also arrive pre-filled from the Calendar Source XML import above (`Initiator/Name`/`Initiator/SmtpAddress`) rather than manual entry — same fields, same validation, same push path either way. **Enforce input limits in the UI** — name/title/email ≤ 32 chars, phone ≤ 16 (live counter, blocks at limit — a frontend concern, e.g. `app.js`'s `cc()`; not re-validated by the Rust backend, which trusts its own frontend as the sole caller). Resize the profile photo to **228×228** JPEG, hard cap 200 KB (`ble-protocol.md` §10, which also has the wire-level byte caps).
- **Clock face preference**: settings subscreen (Digital/Analog), Save/Discard header pattern. On Save, writes Device Settings (`"c"`) only on change (Ori persists to NVS). Orion reads it back on every (re)connect.
- **Seek step**: settings subscreen, single 1–60s slider (default 10), same Save/Discard pattern as Clock Face/Time Format but with no enable toggle. On Save, writes Device Settings (`"k"`) only on change (Ori persists to NVS). Orion reads it back on every (re)connect. Governs how far double-tapping the left/right third of the album art seeks in Controls mode (`media-mode.md`).
- **ANCS notification filter — Orion-driven Auto Do-Not-Disturb schedule** (`notif_filter.rs`, `store::NotificationFilterSchedule`): the user no longer picks one static filter level directly. The Notification Filter settings subscreen instead configures **two** independent levels (Disabled/Call Only/Important/All each) — a **Work Hours** group (defaults to Important — a sensible focus-time default now that narrowing happens automatically) and an **Off Hours** group (defaults to All, matching the old flat setting's own default) — one Save/Discard pair covering both groups at once. Orion itself decides which level is live on Ori's `ancs_filter` (Device Settings `"f"`) at any given moment, computed from `store::WorkHours` (the same start/end/days schedule Weather Alert already reads, `reminders.rs`):
  - **In the window**: `minutes_of_day` within `[start_minutes, end_minutes)` on a configured working day → `work_filter`. Handles `start`/`end` in either order — `start < end` is a normal same-day window, `start > end` is treated as overnight-spanning (`now >= start OR now < end`), and `start == end` is a zero-width window (never "in work hours", not "24 hours" — there's no UI signal for all-day to justify guessing that way).
  - **Everywhere else** (including every minute of a non-working day) → `off_filter`.
  - Pushed unconditionally on every (re)connect (`notif_filter::push_last_known`, `start_post_sync_tasks` — same idempotent "resending costs nothing" treatment as weather/holiday, since Ori's actual value may be stale after any amount of disconnected time). A background 60s tick (`notif_filter::spawn_poll_task`) catches a work/off-hours boundary crossed while Orion stays connected straight through it — the one case a reconnect-triggered push can't cover. Saving either the schedule (`save_notif_filter_schedule`) or Working Hours (`save_work_hours`) also triggers an immediate recompute-and-push (`notif_filter::push_now`) so a Settings change while connected takes effect right away rather than waiting for the next tick.
  - Ori's own `ancs_filter` semantics are completely unchanged — it still just applies whatever single `"f"` value it's told, NVS-persisted, write-only-on-change (`ble-protocol.md` §3/§6.4); only Orion's decision of *what* to write, and *when*, is new. No wire-format change.
  - No offline-edit pending/flush handling needed (unlike Clock Face/Time Format) — there's nothing to "flush," since `notif_filter.rs` always recomputes its current value fresh from persisted settings + the wall clock rather than replaying a queued edit.
- **Ori Info/Stats modal**: tapping the header device name/connection state opens a read-only snapshot — name, connection dot, live signal bars, firmware version, Bluetooth address, serial number, manufacture date, iPhone bond, last-synced time. Merges `get_ori_info` (Rust, cached-only) with a live `read_device_settings` (char `000E`) read for signal bars/serial/manufacture date (piggybacked there — `ble-protocol.md` §4/§6.4). Serial/manufacture date are cached client-side so a disconnect doesn't blank them; signal bars are NOT cached (0 bars while disconnected — "don't show what can't be verified"). **Live while open**: Ori pushes a fresh Device Settings notify (char `000E`) whenever its own live signal_bars bucket changes (~every 5 s if it moved — `ble-protocol.md` §6.4, added 2026-07-13, replacing an earlier ~3 s poll on Orion's own side), which the frontend's `'device-settings-update'` listener applies directly if the modal is open — no redundant re-read. Also refreshed by immediate push-driven updates off `setConn()` and `setPhoneBondStatus()`. See `provisioning.md` for how serial/manufacture date get onto the device and why they survive a firmware update and a factory reset.
- **iPhone/iPad Info/Stats modal + ANCS drill-down**: tapping the header phone icon (bonded, connected or not) opens a snapshot mirroring Ori's own — name, device type/model subtitle, connection dot, live signal bars, battery level, missed-calls/messages/notifications counts (`PhoneBondStatus`, char `000F`), Unpair. Counts arrive already filtered through `ancs_filter` (same gate as Ori's on-device tiles); Orion just displays them, no local filter logic. Device type is already resolved from Apple's raw hardware identifier (e.g. "iPhone18,2" or "iPad14,3") to a marketing name (e.g. "iPhone 17 Pro Max" or "iPad Pro 11-inch (4th gen) — Wi-Fi + Cellular") on Ori's side (`ble-protocol.md`'s `PhoneBondStatus.d`) — Orion just displays the string as-is. Siblings that would otherwise share one identical name get a short connectivity/radio/region suffix instead (`iphone_model_map.h`), which is why this field is a 63-byte budget, not a short fixed name. **UI text says "iPhone" or "iPad"** wherever it names the bonded device (header tooltip, this modal's title fallback, the Ori Info modal's bond row, the Unpair modal), derived from `device_type`'s prefix via `app.js`'s `phoneKindWord()` helper — the generic "iPhone or iPad" only before the very first model read (`connectivity.md` §2). **Live while open** (2026-07-11): every `PhoneBondStatus` notify, including the ~5 s RSSI poll, re-renders an already-open modal (`setPhoneBondStatus()` re-invoking `openIphoneInfoModal()`, idempotent). Tapping a non-zero count opens a filtered list of the underlying notifications (chars 16–17, §13) — already filtered by Ori, so badge and list are always consistent. **Resynced on every Orion (re)connect** (`resync_orion_relay()`/`resync_orion_call_state()`): chars 16/17 are notify-only with no read/replay of their own, so without a resync a notification or live call present before Orion connected would be counted in the aggregate but never reach Orion's local mirror. Fired from Ori's `onSubscribe()` GATT callback, not the earlier `OrionConnected` event (which fires before `run_sync` starts — a resync that early is dropped, not yet subscribed).

  **Reconnect resync race (found 2026-07) and its fix.** `onSubscribe` can fire two ways: Orion's own CCCD write, or — on a **bonded reconnect** — NimBLE's host stack itself (`ble_gatts_bonding_restored()`) restoring every persisted CCCD the instant encryption resumes, entirely server-side, no write from Orion needed. That second trigger is near-instantaneous, firing before Orion's soonest possible `subscribe()` (which still has to wait through connect → GATT discovery → an encrypted read) can win the race — confirmed on hardware: Ori's resync sent everything correctly while Orion's receiver was still not alive. Reordering on Orion's side alone cannot close this. **The real fix is on the firmware side**: `state_machine::on_reconnect_end()` fires only on a genuine reconnect's `SyncEnd` — causally guaranteed to be *after* Orion has subscribed, since Orion's `run_sync()` always subscribes to chars 0010/0011 before sending `SyncControl{END}` — and calls `resync_orion_relay()`/`resync_orion_call_state()` a second, unconditional, idempotent time. Orion's own `subscribe_ancs_relay_early()` (`central.rs`, subscribing before `run_sync` starts in both `reconnect()` and `submit_passkey`) is kept as a genuine improvement — it removes the extra latency Orion's old code added and guarantees the receiver is alive in time for the firmware-side second resync to land.

  Tapping a row opens a detail view (silent badge top-left, close top-right, dynamic Answer/Decline/Dismiss/Read-all buttons built from the notification's own `pos_label`/`neg_label`/`has_neg_action` — never hardcoded) or, for a ringing/active call, the call view instead. **If Ori reports the open detail's notification removed** (`{op:"remove"}`) while on screen, Orion closes it and returns to the list. Notifications sharing app+title collapse into one row/detail with a stacked-count badge and a single "Read all". Writes `AncsNotificationAction` (char `0012`) on every action tap; never updates its own UI optimistically — waits for the resulting notify.
- **Incoming call takeover**: `AncsCallState{st:1}` (char `0011`) brings the Orion window to the foreground (show + focus + un-minimize) and shows the ringing view. Never fires when `ancs_filter` is Disabled (the notify simply never arrives, so Orion needs no filter check of its own). `st:2` (active) resumes the in-call view with its timer seeded from the relayed elapsed seconds. `st:0` closes whatever call view is open. Both the ringing/in-call view and the header call chip render the calling app's real icon from `"k"` (§13), falling back to a generic glyph only when unrecognised. A call already live before Orion connects shows immediately via Ori's call-state resync.
- **Low battery warning** (Settings > Alert > Low Battery Alert, `store::LowBatteryAlert`): the bonded phone's `PhoneBondStatus.l` (battery %, char `000F`) dropping below a user-configurable threshold (5–30%, 5% steps, default **20%** — matches this feature's original hardcoded behavior) warns the user, only while enabled (`enabled:true` by default, preserving that original always-on behavior for an existing install; disabling closes any open warning immediately). Orion-local only — never pushed to Ori.   Shown **once per dip** either way: `checkLowBattery()` (`app.js`) latches after warning until either the level genuinely recovers above the threshold (a later re-drop warns again, no reconnection needed) or the phone (re)connects, which re-arms unconditionally — so a phone that's already below threshold the moment it reconnects warns again immediately rather than staying silently latched from before the drop. An open in-app modal closes itself on disconnect (battery becomes unverifiable, same policy as everywhere else); a native notification that already fired is left as-is (OS-owned once shown, same as any other Windows toast).

Hidden with no live call. The in-call timer runs independently of whether the modal is open. **Ring color mirrors Ori's own status-bar call tile**: solid yellow (`st:1`, `.ringing`) while unanswered, solid red (`st:2`, `.on-call`) once active — `styles.css`'s ring colors are pixel-matched to firmware `theme.h`'s `COLOR_CALL_RINGING`/`COLOR_DANGER`.

## Panel layout

Orion's only UI surface is a 348 px wide tray-anchored flyout panel, split into two visibility zones:

### Always visible (connected and disconnected)
- **Profile card** — circular photo (228×228 px), name. Tapping opens the profile editor subscreen (Save/Back; live character counters at the Orion-enforced caps).
- **Time Off** — divider-separated; toggle + collapsible destination card (image, destination, date range). Tapping opens the Time Off editor subscreen.
- **Firmware update indicator** — header icon shown only when a newer version is available; tapping opens the update flow.

### Visible when Connected or Disconnected — hidden only during Connecting/Syncing
These rows and subscreens (2026-07-11: revised from "connected and synced only") hide only during **Connecting**/**Syncing** — before the sync that would make their values trustworthy has finished. A gated subscreen left open when either state starts is force-closed (`dismissTransientScreen()`).
- **Clock Face**, **Time Format** (24h/12h) — single-select subscreens, Save/Discard. **Notification Filter** is the same Save/Discard pattern but with two independent single-select groups (Work Hours / Off Hours) in one screen — see the Auto Do-Not-Disturb bullet above.
- **Quick Actions** — three-slot subscreen with per-slot combo recorder for Favorite slots.
- **Seek Step** — single 1–60s slider (default 10), no enable toggle, same Save/Discard pattern. Writes Device Settings (`"k"`) only on change; Orion reads it back on (re)connect. Governs double-tap-left/right seek distance in Controls mode (`media-mode.md`).

**Disconnected differs from Connecting/Syncing: rows stay visible and editable.** The user can Save with no live link — Orion just can't confirm against Ori yet. `save_device_settings` persists the pending value to Orion's local store first (`store::SavedState::pending_*`, survives an app restart) and best-effort attempts the live write, swallowing failure (offline editing is the intended path, not an error). `run_sync` flushes any pending value on the next successful reconnect, alongside the unconditional shortcuts push, then clears the pending flag. Quick Actions needs none of this — its tokens already push unconditionally on every reconnect regardless of dirty-state.

On transition into Connected, Orion re-reads Device Settings (§6.4) to repopulate the rows — by then any pending edit has already been flushed by `run_sync`, so the read reflects the just-delivered value.

### Settings subscreen UX convention (Save/Discard)
- Header: **Back** (left) · title (centre) · **Save** (right, disabled until a change is made).
- Selecting an option/recording a combo arms Save but doesn't apply immediately.
- Back/Esc with no pending change: returns immediately.
- Back/Esc with a pending change: "Discard changes?" modal — **Keep editing** stays with the pending change; **Discard** reverts and returns without writing.
- **Save**: commits, writes to Ori via Device Settings, returns to the panel.

Profile and Time Off subscreens use the same convention but are accessible regardless of connection state.

## Build: CSP is back — inline handlers were migrated to addEventListener

Background on why this was ever unset: a real release build's CSP auto-gets a Tauri-injected `script-src` hash for its IPC bootstrap script, and per spec **any hash/nonce in a directive silently disables `'unsafe-inline'` in that same directive** — this killed every inline `onclick="..."` handler in `app.js`-driven markup (invisible under `tauri dev`, only reproduces in a real release build). Fixed 2026-07 by removing **every** inline event-handler attribute from `index.html` (onclick/onchange/oninput/onkeydown/onpaste, plus the crop canvas's pointer/wheel/touch attributes and the period-calendar's mousemove/mouseleave — same failure mode, not just the ones named `onclick`) and wiring them in `app.js`'s `wireStaticHandlers()` (called once from the existing `DOMContentLoaded` listener) via `addEventListener`, preserving every literal argument/element/event exactly.

`tauri.conf.json`'s `app.security.csp` is set again: `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; connect-src 'self' ipc: http://ipc.localhost`. `script-src` has no `'unsafe-inline'` at all now (nothing inline left to allow) — Tauri's own hash still gets auto-appended, harmlessly. `style-src` keeps `'unsafe-inline'` since inline `style="..."` attributes are still used throughout and Tauri's hash injection never touches `style-src`. `img-src` needs `data:` for profile/Time Off photo previews (`FileReader.readAsDataURL` → `.src`/`background-image`). `connect-src` explicitly allows `ipc:`/`http://ipc.localhost` — Tauri v2's IPC transport needs these listed once a CSP exists, on both the custom-protocol (`ipc:`) and WebView2 (`http://ipc.localhost`) paths.

**Do not add new inline `on*="..."` attributes to `index.html`.** Wire new UI actions the same way: element gets/keeps an `id`, listener goes in `app.js`'s `wireStaticHandlers()` (or a dedicated function for anything created dynamically at runtime, e.g. `openAncsDetail`'s built-in-JS buttons already do this).
